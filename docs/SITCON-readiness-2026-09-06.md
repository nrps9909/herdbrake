## 相對 9/5 已補足

- 實際三部門 Qwen 推論，保存原始提示、回應與來源；另有 live API 建立持久批次的實測。
- 影片主線使用明確標記的同一份推論重現，能穩定展示「單筆合法、整批超額、部分核准、再次超額被拒絕」。
- 模型理由即使算錯也不覆寫成漂亮答案；固定政策獨立控制累計流出，提供可重算證據。
- 55 個單元／SQL 測試、7 個 HTTP 整合測試、相依弱點清查，以及可執行 CI。
- MIT、公開來源位置、技術文件、來源揭露、操作指南及提交摘要。

## 評分上的強項與弱項

| 面向 | 判斷 |
| --- | --- |
| 問題與影響 | 能清楚說明多個部門代理各自合理、合併卻超出現金底線的情況；仍缺財務人員訪談與實際發生頻率 |
| 技術 | 具備模型→提案→確定性檢查→人工核准→後端交易→證據的實際流程，能展示 UI 以外的拒絕結果 |
| 展示 | 精簡為一個 12 筆案例，讓評審先理解 5.4m 超額、2.7m 可核准，再看重複核准仍受限制 |
| 開源 | 無金鑰也能重現核心流程；模型錄製、測試與限制公開，適合評審自行檢驗 |
| 成熟度 | 是本機已驗證的黑客松原型；正式部署、多人雙人覆核、跨批次共享餘額與真實付款仍未完成 |
| 差異化 | 應強調多代理付款前的累計風控與稽核，不宣稱金融 AI 或風控本身首創 |

## 截稿前與現場的做法

優先完成公開影片與提交。沿用已登記的主賽道，沒有實際鏈上金融整合時不勾國泰 Bounty；雜湊鏈不是區塊鏈。不要為了增加技術名詞臨時加入無法驗收的付款或智能合約。

若現場能找到財務／出納使用者，可做一次真實短測：先給原始 12 筆清單，再操作 HerdBrake，記錄是否理解整批風險、完成核准所需時間及最困惑的地方。取得使用者同意後再引用；沒有測量就不填「節省時間」或「避免損失」。

問答可直接承認：目前額度以單批為界、換匯為政策快照、核准未真的付款；下一步最有價值的是連接同一資金池的跨批次預留與雙人覆核，而非再增加圖表。AI 模型可以出錯，但金額與核准限制不依靠模型自我約束。

我會將目前作品評為 **有清楚技術主線、值得參賽；前三仍需靠問題價值與展示說服力爭取**。沒有看過所有對手與評審實際評分，無法給可信的得獎機率。
